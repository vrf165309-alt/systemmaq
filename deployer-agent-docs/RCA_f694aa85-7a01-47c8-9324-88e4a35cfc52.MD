# RCA — HTTP 520 em POST /api/auth/login (produção mastermaq-system.online)

Run analisado: `f694aa85-7a01-47c8-9324-88e4a35cfc52` (redeploy, status **success**, promovido)
Template: `fastapi_react_mongo_shadcn_base_image` · frontend_type: **cloudflare** · target_cluster: `target-7` · tier: **tier_0**

## TL;DR
O deploy foi bem-sucedido e o **backend de produção está saudável**. As hipóteses levantadas (backend crashado, env não propagada, import novo quebrado, incompatibilidade de `Request`) foram **DESCARTADAS por evidência**. O 520 **não é um bug no código de login** e **não é falta de env var**. As requisições de login **não estão chegando ao backend de origem** — o erro nasce na camada de borda (Cloudflare/conexão-origin), com forte contribuição de **pressão de memória no tier_0 causada pelo Playwright/chromium do auto-sync**.

## Evidências coletadas
1. **Deploy OK e pods saudáveis**: run ativo `success`/promovido. Ambos os pods `phase=Running`, `ready=true`, `restart_count=0`. Sem `OOMKilled`, sem `last_termination`, sem CrashLoop. `kill_findings` só mostra "Startup probe failed: connection refused" durante o boot (janela 23:54:33–23:55:08), enquanto o chromium era instalado — depois disso os pods ficaram prontos.
2. **Startup completo**: logs mostram `Application startup complete`, `Uvicorn running on http://0.0.0.0:8001`, `Master admin seeded/validated`, `Supabase DB adapter initialized`, `SUPABASE_URL configured: Yes`.

4. **Login NÃO chega ao origin**: em **1440 min** de log, a única linha em `/api/auth/login` é o meu probe GET (404 — esperado, rota é POST). **Zero POST `/api/auth/login`** — as tentativas do usuário não são registradas pelo uvicorn ⇒ não alcançam o backend.
5. **Todas as env vars presentes e não-vazias** (run ativo): `MONGO_URL`, `DB_NAME`, `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `SUPABASE_ANON_KEY`, `JWT_SECRET`, `TELECONTROL_LOGIN/PASSWORD`, `TELECONTROL_LOGIN_HQ/PASSWORD_HQ`, `TELECONTROL_BASE_URL`, `WA_APP_ID/WA_APP_SECRET/WA_PERMANENT_TOKEN`, `ASSINAFY_API_KEY/API_URL/WORKSPACE_ID`, `CORS_ORIGINS`, `APP_LOGIN_EMAIL/PASSWORD`, etc.

6. **Ruído dominante e relevante — Playwright/chromium**: o loop de auto-sync Hisense (`Auto-sync HISENSE loop started: every 30 minutes`) tenta lançar o chromium repetidamente e falha em massa:
   - `BrowserType.launch: spawn ETXTBSY` (binário sendo escrito/instalado enquanto é executado — corrida de first-boot install)
   - `BrowserType.launch: Executable doesn't exist at /root/.cache/ms-playwright/.../chrome-headless-shell`

   - Origem no código: `telecontrol_scraper.py:82` (`start_browser`) chamado por `telecontrol_scraper.py:1048` (`_sync_orders_impl`).

- "Backend crashou no boot em produção" → **FALSO**. Pods ready, sem restart/OOM, startup completo.
- "Env não propagada (MONGO_URL/DB_NAME/SUPABASE/TELECONTROL...)" → **FALSO**. Todas presentes e não-vazias.

## Causa-raiz (diagnosticada, não reproduzida)
O 520 é da borda Cloudflare: o edge não obtém resposta válida do origin para as chamadas de API do **domínio custom**, e a requisição **não é registrada pelo uvicorn**. Duas camadas contribuem:

**(A) Pressão de memória no tier_0 (mais provável e acionável).** tier_0 = **512Mi** de limite de memória, 250m CPU, 2 réplicas. O app empacota Playwright + chromium (imagem de 868MB) e o loop de auto-sync Hisense lança chromium a cada 30 min. Um chromium headless sozinho consome ~300–500MB. Quando o chromium sobe junto do uvicorn no mesmo cgroup de 512Mi, o OOM-killer do kernel mata o maior processo (o próprio chromium — daí as falhas de launch e `restart_count` do container permanecer 0), mas durante os picos o pod fica sob starvation e conexões TCP recém-chegadas podem ser recusadas/resetadas → o edge Cloudflare recebe resposta vazia/reset → **520**, sem que a request chegue a ser logada pelo uvicorn. Isso também explica o `connection refused` do startup probe durante a instalação do chromium.

**(B) Camada de borda/rota do domínio custom (não inspecionável pelo meu toolset).** Não tenho ferramentas para ler KV/worker/hostname/SSL da Cloudflare. O padrão "200 em emergent.host + 520 no domínio custom + zero log no origin" pode também indicar problema específico de rota `/api/*` do custom hostname. Precisa do teste de isolamento abaixo.

## Ações recomendadas (para E1/usuário aplicar — NÃO aplicadas por mim)
1. **Teste de isolamento (rápido, decisivo)**: faça o login apontando para `https://sync-hub-preview-1.emergent.host` (domínio nativo) com as mesmas credenciais.
   - Se **funcionar** no emergent.host e **520** no mastermaq-system.online ⇒ problema de borda/custom-hostname na Cloudflare → escalar para o suporte Emergent (fora do meu alcance de ferramentas).
   - Se **também 520** no emergent.host ⇒ confirma o fator (A) origin/memória.
2. **Aliviar a pressão de memória (fix principal do lado do app):**
   - **Upgrade de tier**: tier_0 (512Mi) → no mínimo **tier_1/tier_2** para dar headroom ao chromium. (Feito no Painel de Deploy → Resources.)
   - **e/ou desativar o auto-sync automático do Hisense**: hoje `HISENSE` roda em loop a cada 30 min (o HQ já está "manual only"). Tornar o Hisense também manual (só via botão "Sincronizar") elimina os spawns periódicos de chromium. Ponto no código: o loop iniciado no startup do `server.py` ("Auto-sync HISENSE loop started: every 30 minutes").
3. **Corrigir a instalação do Playwright (elimina ETXTBSY / "Executable doesn't exist")**: instalar o chromium em **build time** (no Dockerfile, ex.: `RUN playwright install --with-deps chromium`) em vez de no primeiro boot. Isso remove a corrida de first-boot e as 367 falhas consecutivas de launch, reduzindo o churn de subprocesso e a pressão de memória no boot.

## Observações
